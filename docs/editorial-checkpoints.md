# Recovery of paid editorial substeps

The worker persists model responses and rendered candidates remotely before advancing. A render retry on another process or host reuses the paid direction, validated edit inputs, and exact candidate bytes. Registration failure retrieves the reviewed MP4 and submits it again without another model or render call.

## Scope and ownership

- `studio_editorial_checkpoints` is service-only with RLS and no browser grants.
- The RPC derives user/project from a live render lease, and checks the production parent when present. A caller cannot supply an arbitrary customer namespace.
- A request key includes the recovery protocol, immutable render/project inputs, model profile, exact instructions/schema/context, and visual evidence. Changed assets, script, customer preferences or model invalidate reuse. Identical duplicate memory entries are normalized; distinct instructions stay intact.
- GPU/source media are not regenerated by editorial recovery.
- MP4 checkpoints use a SHA-256 path in private `studio-media`. Downloads and duplicate-upload conflicts verify bytes before reuse. Existing quality validation remains mandatory.

## Failure behavior

1. Model requests reserve a durable `started` marker before dispatch. The result and usage receipt are saved before validating or proceeding to another model.
2. Completed responses are reused. Known failed requests permit at most one additional attempt for the same request key. Unknown/in-flight paid requests stop with `EDITORIAL_CHECKPOINT_UNCERTAIN` rather than risking a duplicate charge.
3. Rendered candidates are uploaded before visual review. If review fails, the next attempt downloads that exact candidate and only retries the required review. Artifact work may be reclaimed after a dead worker because it does not dispatch a paid model.
4. The final review/result is checkpointed before delivery. A delivery retry bypasses the editor and source downloads. A schema/validation error stays blocking; checkpoints do not override a failed review.
5. Costs reused from other attempts are recorded under `usage.reusedCalls`, separate from new `usage.calls` and `usage.total`. The original charge remains on the original run; replay does not charge it again.

The recovery protocol is `editorial-recovery-v1`. Bump it for semantic changes to rendering or review acceptance that must invalidate old completed results. Model request keys also include their exact prompts/schema and profile automatically.

## Deployment

Apply `20260915205433_editorial_checkpoints.sql`, deploy Pages API, then the Render worker. No new GPU or model calls are needed. The API returns `job.recovery`; old jobs/API responses without it retain the legacy behavior during rollout. Existing local-only receipts are not imported or silently trusted.

## Validation

Offline tests cover DeepSeek failure after direction, review failure after rendering, registration failure across hosts/jobs, response loss after saving a checkpoint, ambiguous provider usage, bounded retries, changed inputs/models, media corruption, concurrent claims, owner isolation and expired leases. The existing real-FFmpeg render/review regression is also run. These are injected failures, not a claim of a new autonomous customer delivery.

Unresolved limits: a provider response lost before its durable result is saved cannot always be reconstructed. It stays blocked for reconciliation. Checkpoints currently follow project/render ownership lifecycle; private MP4 retention should be included in storage accounting and future cleanup policy.
